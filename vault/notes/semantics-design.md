# HeptaSync v1 — 語意與互動設計(白話版)

> 這張卡是 2026-05-22 一場設計討論的白話總結。完整、精確的版本在 repo 的 `v1/DESIGN.md` §8。這裡只求好懂。

## 一句話

HeptaSync 補的是官方 Heptabase CLI 缺的那一個動作:**「改寫一張已經存在的卡」**。官方 CLI 只能新建卡、往卡的尾巴加東西,改不了中間。HeptaSync 就補這個洞。

## 怎麼用

1. 想改某張卡 → `hs pull` 把它變成本地一個 `.md` 檔。
2. 像改一般文字檔一樣編輯它。
3. `hs push` 推回 Heptabase —— 還是同一張卡,身分不變。

找卡、建全新的卡,還是用官方 CLI 比較簡單;HeptaSync 專心做「改既有卡」這件事。

## 講定的幾件事

### 同步

- 一個資料夾 = 一個 vault,綁在專案目錄(就像 git 的 `.git/`)。
- 卡片標題 = 內文第一行的 `# 大標`。改它就會改卡名,兩邊雙向。
- 檔名只是給人看的,工具**永遠不會自動改你的檔名**。
- 本地把檔案刪掉 **不等於** 刪卡片,只是「不再同步它」。要真的刪卡得明講 `hs trash`。
- v1 只做 note 卡片;journal 跟白板暫時不碰。

### 動到真實資料時

- 單檔 `hs push` → 直接做,做完回報。
- 整批 `hs sync` → 先給你一份「會改哪些」的清單,你點頭才整批寫。
- 平常安靜,只有「動到真資料 / 出狀況 / 要你決定」才開口。
- 卡片太大(超過 10 萬字)推不回去 → 停下來,建議切成兩張,你同意才切。
- 你 pull 之後別人也改了同一張卡 → 工具把你的版本備份成 `.conflict.md`,**不會硬蓋掉**,然後告訴你。

### Tag

- 新卡不主動問你要掛什麼 tag —— 你 frontmatter 寫什麼就掛什麼。
- 打錯字會憑空生出垃圾 tag(而且 CLI 刪不掉)→ 工具發現「新 tag 長得很像某個舊 tag」會停下來問你。
- tag 同步用「三方比對」:你加的、你刪的、遠端自己多出來的,互相不會蓋掉。

### 檔案開頭那段隱藏設定(frontmatter)

- 每個 `.md` 開頭有一段 `heptabase:` 設定,記住這檔對應哪張卡。預覽 markdown 時看不到。
- 你能自己改的只有 `tags:`;其他欄位是工具管的,別手動動。
- 你寫一個全新的純 `.md` 直接 push,工具會自動幫你補上這段設定。

## ⚠️ 我覺得你還需要額外想的

1. **journal 沒進 v1,但 journal 可能才是你最常用的。** 你每天在 Heptabase 寫 journal(LeetCode 紀錄那些)。journal 技術上跟 note 幾乎一樣、加進來很便宜。要想清楚:v1 切「只做 note」,是不是剛好把你最高頻的用途排除掉了?
2. **判斷邏輯要放程式裡,還是交給 Claude?** 像「卡太大要不要切」「衝突怎麼辦」「tag 像不像」這些判斷,還沒決定是 `hs` 程式自己做,還是 `hs` 只負責回報、由 Claude 讀完再決定。這會大幅影響怎麼實作,值得先想。
3. **同一張卡可能同時待在兩個 vault。** 你選了「每個專案一個 vault」。代價是同一張卡被 pull 進專案 A 跟專案 B,兩邊各改會打架。工具靠衝突機制接住、不會掉資料,但用起來會煩 —— 想一下這在你身上會不會常發生。
4. **白板在 v1 是唯讀的。** 你本來以為 `whiteboards` 欄位可以編輯,但 v1 不寫白板。確認一下你 OK 在 v1 沒有「用 frontmatter 把卡丟上白板」這個功能。
